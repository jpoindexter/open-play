# Hardware tempo control after Smart Sync

18 October 2026, browser source based on a0dd5a0. **The current desktop0.1.21 does not contain this fix. Physical Hercules acceptance and full parity remain open.**

The reproduced blocker was concrete: a100BPM track synced to120BPM has a20% software rate. The MIDI router required an absolute ±8% fader to cross that20% target. It therefore ignored every movement. The first controlled reproduction had five failures among six cases; the ordinary absolute-pickup case passed. The earlier REL label alone did not implement hardware relative tempo.

The official [relative-pitch article](https://support.serato.com/hc/en-us/articles/227561947-Relative-Pitch-Tempo-Control-Smart-Sync) documents fader movement while synced or in REL, shared synced tempo, hardware Shift repositioning, and leaving REL through OFF/reload. [Disengage Sync](https://support.serato.com/hc/en-us/articles/227561927-Disengage-Sync) distinguishes the first and second OFF presses. These are qualitative documented contracts; no proprietary response code, numerical taper or hardware timing was recovered or copied.

Production MIDI routing now treats absolute hardware travel as a movement coordinate during Smart Sync/REL. The first unknown packet establishes a no-jump baseline. Subsequent movement offsets the current software rate; a shared software-tempo change rebases against the last physical position. Shift-ignore moves only that baseline. Rate limits consume saturated travel so reversing responds immediately. Requests coalesce while the engine is busy and queued work is scoped to the track. Ordinary non-relative pickup remains in place.

The router remembers each deck's latest received absolute physical position. The second OFF press and a normal reload from REL call its reset through the actual app/panel path. Known hardware position restores immediately, recalculated for the current pitch range. With no received position, software tempo is preserved and the next actual packet gets explicit absolute takeover instead of an unreachable pickup target. Disconnect invalidates cached device positions. This does not establish every reconnect, simultaneous-input or in-flight failure race.
