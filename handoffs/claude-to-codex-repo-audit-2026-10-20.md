**What this repo does:** Open Play is a local, single-user DJ app. A browser prototype (`prototype/`, plain ES modules, Web Audio, no bundler) runs two decks with cues, loops, Sync, keylock, stems and effects, and is hosted either by a Python dev server (port 8848) or inside an Electron shell (`desktop/`, local HTTP on 18775) packaged into test builds. State lives in one `localStorage` key and imported audio bytes in IndexedDB.

**Load assumed:** one DJ on one Mac, sessions of several hours, a personal library of a few hundred to a few thousand tracks, two decks playing real-time audio at 44.1/48 kHz. "Holds under load" here means: does not stall or click while music plays, and does not run out of memory or storage during a normal night.

## Must fix

1. **Decoded audio for every touched track stays in memory for the whole session** (`prototype/engine.js:149-157`; callers `prototype/app.js:1141,1149,1230`, `prototype/stems.js:94`, `prototype/sync.js:86`)
   - **What this is:** `engine.buffer()` decodes a track into float samples (about 230 MB for a 10-minute stereo track at 48 kHz) and keeps it in a Map. Load, import, analysis, stem prep and Sync all call it. Nothing in the engine ever removes an entry; the only clear is a manual button in the System panel.
   - **Problem:** Drag 30 files into the library → about 3 GB kept before analysis starts, because import decodes each file to read its length. "Analyze all" on 400 tracks asks for about 40 GB. The renderer dies first. This also explains the >2 GB resident memory seen with both decks stopped.
   - **Fix:** After import and after each analysis job, drop the buffer unless a deck holds that track: `if (!state.decks.some(d => d.track?.id === t.id)) engine.buffers.delete(t.id);` (three one-liners). Add `engine.releaseTrack(id)` (delete from `buffers` and `stemBuffers`) and call it from deck unload at `app.js:910`. Analysis and import can instead decode through a throwaway `OfflineAudioContext`, as `library-waveform-preview.js:66` already does.
   - **If we skip it:** Importing a real library crashes at roughly 20–40 files, every time.

2. **Saving stops working after a few hundred analyzed tracks, and cues set after that are lost on reload** (`prototype/app.js:207-272,1245`; `prototype/analysis.js:386`)
   - **What this is:** `persist()` writes the whole library state to one `localStorage` key on every change. Each analyzed track carries `analysisResult`, which includes a `grid.beats` array (one number per beat of the analyzed 180 s). `result.grid` and `result.tempo.grid` are the same object, so the array is written twice. Measured: about 13,000 characters per track, 11,700 of them this array. Nothing in the app reads `beats`.
   - **Problem:** Chromium allows about 10 MiB per origin (5 MiB in other engines). At roughly 400 analyzed tracks (200 elsewhere) every save throws, the `catch` at `app.js:267` shows a 3.5-second toast, and the stored copy freezes. Every cue, loop, grid edit and play after that moment is gone at the next launch. The `beforeunload` save fails silently too.
   - **Fix:** At `app.js:1245`, before storing: `delete result.grid?.beats;` (the aliased copy loses it as well). Per-track cost drops to about 1,200 characters. Also make the storage-failure notice stay on screen instead of auto-hiding.
   - **If we skip it:** The DJ finds out on the next launch that last night's cues are gone, with no clue why.

3. **A wrong-typed field in saved state or a backup blanks the app, breaks every cue press, or freezes the clock** (`prototype/app.js:57-101,866-868,598-630,1958-2036`; `prototype/panels.js:466-511`)
   - **What this is:** Boot parses saved JSON inside a try/catch (good) but then trusts the shape of `crates`, `prepare`, `history`, `localTags` and `settings`. Restore-backup checks only the `format` field and copies settings and 14 track fields as they come.
   - **Problem:** Three concrete cases. (a) `{"crates":{}}` in storage: `saved.crates || [...]` keeps the object, `state.crates.filter` throws during module load → blank page, no reset button reachable. (b) A backup with `"Quantize Value": 1` (a number): `state.settings["Quantize Value"].includes` is not a function at `app.js:867` → every cue, hot cue, loop and roll press errors while quantize is on. (c) A backup track with `"cues": null` or a warp marker with `time ≥ duration`: `drawDetailWave` or `createBeatgrid` throws inside `tick()`, and because `requestAnimationFrame(tick)` is the last line, the frame loop never restarts: time readouts, meters and sync indicators freeze while audio keeps playing.
   - **Fix:** About ten lines. `Array.isArray(saved.crates) ? saved.crates : defaults` (same for `prepare`, `history`; object check for `localTags`). In restore, accept a backup value only when `typeof` matches the live default. Wrap the body of `tick()` in `try { … } finally { requestAnimationFrame(tick); }`.
   - **If we skip it:** The hand-edited backup that the app recommends as the recovery path for finding 2 can brick the library until DevTools clears storage.

4. **Every desktop build silently cannot prepare stems for tracks longer than about 6 minutes** (`desktop/server.cjs:21,24-25`; `prototype/stems.js:99-119`)
   - **What this is:** The Electron host proxies `/api/stems…` to the Python service. It allows at most two path segments after `stems` and rejects any POST body under 44 bytes. The renderer uses a chunked upload for decoded audio over 128 MiB (stereo float at 44.1 kHz: anything over ~6:20): it POSTs a 17-byte JSON body to `/api/stems/uploads`, then chunks, then `POST /api/stems/uploads/<id>/commit` (three segments). `server.cjs` is copied into every build (`desktop/package-playback.mjs:37`).
   - **Problem:** `POST /api/stems/uploads` with body `{"size":200000000}` → 413 "WAV must be 44 bytes to 128 MiB". With the floor lifted, the commit URL still gets 404 from the two-segment regex. The error text blames the file. Under the Python dev server there is no proxy, so browser tests never see this.
   - **Fix:** `{0,2}` → `{0,3}` on line 21; apply the 44-byte floor only when the path is exactly `/api/stems` (Python already enforces per-route limits); stop overwriting `content-type`. Add one proxy case for the chunked route to `scripts/test_desktop_server_review.cjs`.
   - **If we skip it:** Stems never work for long tracks in any desktop build; any desktop stem evidence so far covers sub-6-minute tracks only.

5. **Every deck load copies the whole track into a scratch worklet; stemmed tracks over ~5 minutes fail to load scratch** (`prototype/app.js:774` → `prototype/engine.js:1449-1477` → `prototype/deck-scratch.js:21,51-67`)
   - **What this is:** `preloadDeckScratch` runs on each load. It copies every channel of the original plus all four stems, sample by sample, into fresh arrays and sends them to the audio thread. The worklet has a 512 MiB budget that the engine never changes.
   - **Problem:** A 10-minute track with stems is 5 × 230 MB = 1.15 GB → `RangeError('Scratch PCM exceeds configured 536870912-byte memory budget.')` shown as a toast on every load of a stemmed track longer than ~4:40 at 48 kHz. Without stems the copy succeeds and each idle deck holds a second full copy: two stopped 10-minute decks ≈ 460 MB in the engine plus 460 MB in worklets. The copy loop also walks ~58 M samples on the main thread right after load, competing with the first Play and the waveform paint.
   - **Fix:** Delete `app.js:774`. `beginDeckScratch` already preloads lazily on first touch (`engine.js:1604`) and the "Preparing scratch…" state exists for that wait.
   - **If we skip it:** Scratch is broken for long stemmed tracks and idle memory per deck is doubled.

6. **Keylock with a loop or reverse re-renders the entire track, never caches it, and fails outright past ~8 minutes with a key shift** (`prototype/engine.js:477-492`; `prototype/keylock.js:45-51,76-82,112-118`)
   - **What this is:** For a keylocked deck with Loop or Reverse on (non-warp path), `start()` renders the full original and all stems through the pitch worker to loop a few beats. Results over 128 MiB are never cached; renders needing more than 512 MiB of working memory are refused.
   - **Problem:** Keylock on, Loop on, nudge pitch five times → five full-track renders, each several seconds of "processing", zero cache hits. With any key shift the guard needs about three times the track length in memory, so a track longer than ~7:50 at 48 kHz cannot be looped or reversed with key shift at all ("This track exceeds the browser pitch-render memory limit"). The warp-loop path already renders only the loop region (`keylock.js:28-31`).
   - **Fix:** In `start()`, when `d.loop && !d.reverse`, slice each buffer to `[loopIn, loopOut]` before `render()` and subtract `loopIn` from `loopStart`, `loopEnd` and the start offset, as `renderWarpLoop` does (~15 lines). Route reverse-without-loop through `startForwardKeylock` with `reverse:true`, which already exists.
   - **If we skip it:** Multi-second stalls on every loop or pitch change for long keylocked tracks, and a hard failure on long tracks with key shift.

7. **`setRate` has no tempo bounds and no rollback, so a bad fader or MIDI value wedges a deck** (`prototype/engine.js:721-802`)
   - **What this is:** The pitch fader, `deck-midi.js` and `jog-bend.js` all enter here. Sibling paths (`setJogBend`, the sync path, the renderer) bound tempo to 0.25–4×. `setRate` does not. On its restart path it sets `d.rate = rate` and then awaits `start()` with no try/catch.
   - **Problem:** `setRate(d, 5)` on a plain deck plays at 5×. On a keylocked, looped or reversed deck, `start()` throws from `validateTransform` (for example keyShift +12 at rate > 2 exceeds the ±24 semitone limit); the deck is now paused with the rejected rate still stored, and the next Play fails with the same error.
   - **Fix:** First line: `if (!Number.isFinite(rate) || rate < .25 || rate > 4) throw new RangeError('Tempo must be 0.25–4×.');`. At the restart branch keep `const previous = d.rate;` and on a thrown `start()` restore it, mirroring the live-keylock path at `engine.js:766-768`.
   - **If we skip it:** One stray controller value leaves a deck that cannot play until the control is moved back.

8. **Saved grids extend a single tempo over the whole track, so tracks with tempo wobble go audibly out of time after the analyzed window** (`prototype/analysis.js:261-264`, `prototype/app.js:98,1255-1261`)
   - **What this is:** Tempo analysis covers the first 180 s (`maxSeconds: 180`), fits one BPM and one first-beat time, and `createBeatgrid` extends that forever. Smart Sync aligns those grid lines exactly.
   - **Problem:** Measured on the user's own track (details in the Sync report): Can You Feel It's kicks run 8–37 ms ahead of its saved grid after 3:00, so a perfectly grid-aligned mix is audibly off in the second half. The app shows aligned lines over out-of-time audio and says nothing.
   - **Fix:** After the constant fit, score the pulse onsets against the fitted grid in sliding windows over the full track; when the windowed residual exceeds about 10 ms, add `tempo_drift_detected` and `grid.warpSuggestions: [{time, bpm}]`, and show them in the Edit grid dialog as one-click stageable Beat Warp Markers (never auto-applied). Regression: extend `scripts/test_analysis_core_tempo.mjs` with a two-tempo synthetic (115.54 BPM for 150 s, then 115.60) asserting the flag and a marker within ±5 s / ±0.03 BPM. Optional: store the exact fitted BPM instead of `Math.round(bpm*100)/100` at `app.js:1256` (removes a further 5–8 ms on long tracks).
   - **If we skip it:** CORE-FIX-07 stays open; every old house record mixed past its third minute needs a manual nudge.

9. **Track colour from a backup is injected into HTML without escaping** (`prototype/panels.js:496-500,~364`; `prototype/app.js:395`)
   - **What this is:** Restore-backup copies `color` as-is. The art grid writes `style="--art:${t.color}"` and Track details writes `<input type="color" value="${t.color}">` without `esc()`. Crate colours are already checked with a regex; track colours are not. Every other title/artist/comment sink checked uses `esc()`.
   - **Problem:** A shared backup with `"color": "\"><img src=x onerror=alert(1)>"` runs script when the user opens the art grid or right-clicks that track. In Electron this runs with the app's permissions (MIDI, speaker selection, local server).
   - **Fix:** `esc(t.color)` at both sites, or reuse the crate colour regex in the restore whitelist. Two edits.
   - **If we skip it:** The recovery path the app recommends is an unescaped script sink.

## Should fix

10. **The ordinary Sync handoff schedules the swap 30 ms ahead and never checks whether it is already late** (`prototype/engine.js:496-531`; compare `prototype/sync-tempo-handoff.js:15,20`)
    - **What this is:** Plain `synchronize()` (all Smart/Simple Sync callers) and slicer loops fix `when = now + 0.03`, then do alignment math, grid timeline, reverse planning and buffer-source creation before calling `source.start(when)`. The old voice fades out over 10 ms at `when`; the new one fades in. The group-tempo path uses 100 ms and refuses to start if the lead was missed; the keylock path uses 50 ms plus the adapter's acknowledged time.
    - **Problem:** If the main thread hitches for more than 30 ms between those two points (a garbage collection of one of the 230 MB arrays from findings 1, 5, 6, or a waveform paint), Web Audio clamps the past time to "now": both fades become hard cuts and the new voice starts at a position computed for the earlier time. That is a click plus a small jump. This is a plausible, not reproduced, mechanism for the intermittent Sync pop (CORE-FIX-01). The captured 0.1.32 launch was not late.
    - **Fix:** Use `+0.1` at line 498 and, right before `source.start`, `if (this.ctx.currentTime > when - .005) throw new DOMException('Sync start missed its lead.', 'AbortError');`. `synchronize` already treats AbortError as superseded and restores the rate; the old voice keeps playing. Trade-off: a very late press becomes a silent no-op instead of a click. Verify by recording the master and pressing Sync while the analysis queue runs.
    - **If we skip it:** Clicks whenever the main thread hitches, which findings 1, 5 and 6 make routine.

11. **A zero-length or inverted saved loop reaches the audio source and desynchronizes audio from the clock** (`prototype/engine.js:803-851`; `prototype/manual-loops.js:18,37`; `prototype/loop-pads.js:31`)
    - **What this is:** `setLoop` never checks `end > start`. The Loop Out button guards it in the UI, but saved-loop restore and loop pads pass stored bounds straight through.
    - **Problem:** With `loopStart >= loopEnd`, Web Audio loops the whole buffer: audio restarts from the top while the deck clock runs to the end and parks there; `onended` never fires. On the grid path the modulo is `NaN` → "Invalid synchronized source position".
    - **Fix:** First line of `setLoop`: `if (on && !(start >= 0 && end > start)) throw new RangeError('Loop Out must be after Loop In.');` — the same rule already exists as `hasLoop` in `manual-loops.js:8`; move it into the engine.
    - **If we skip it:** A stale saved loop puts a deck into audio/clock mismatch that only Stop clears.

12. **Autoplay starts the next deck even when its load failed** (`prototype/app.js:1942-1956`)
    - **What this is:** `load()` returns `true` only when the track decoded and the request is still current. `engine.onEnd` ignores that and calls `play()` anyway.
    - **Problem:** Autoplay on, next track missing or undecodable: one error toast from load, a second from play, and the deck sits on a track that cannot play, at the one moment autoplay exists for.
    - **Fix:** `if (await load(d.index, a[i + 1].id)) await play(d);` — one line.
    - **If we skip it:** Silence plus two error toasts at the end of a track with hands off.

13. **Play counts reset to zero on every reload, and history shows UTC instead of local time** (`prototype/app.js:207-236,838,842`; `prototype/panels.js:490-505,1525,1531,1544`)
    - **What this is:** `play()` increments `track.plays`, but `plays` is not in the list of fields `persist()` saves, nor in the backup restore list. History timestamps are stored as ISO UTC (fine) but the History panel and the CSV export print the raw string.
    - **Problem:** Play 40 tracks, restart → all counts are 0, the Plays column is blank, and a smart crate on "play count ≥ 1" is empty. A set played in Valencia at 23:30 shows and exports as 21:30Z.
    - **Fix:** Add `"plays"` to `metadataFields` at `app.js:236` and to the restore whitelist (two tokens). `new Date(h.time).toLocaleString()` at render and in the CSV map only; keep ISO in storage.
    - **If we skip it:** A visible column and a crate rule that are always wrong after the first restart; every history timestamp 1–2 hours off.

14. **Re-analysis with tempo and key both switched off still runs the full spectral pass** (`prototype/analysis.js:324-373,374,382`; callers `prototype/app.js:1235-1236`, `prototype/panels.js:2037-2038`)
    - **What this is:** The two flags only decide whether the final tempo and key calls run. The 2048-point FFT at a 128-sample hop (16× overlap) runs for every frame regardless. Locked tracks are re-analyzed with both flags off; Settings exposes both checkboxes.
    - **Problem:** Measured on a 10-minute mono track: both on 5.3 s, both off 6.2 s. "Re-analyze all" over a library of locked tracks pays about 1.8 s per track (at the 180 s cap) for a gain and loudness result that costs about 0.3 s. The work runs in the analysis worker, so the UI does not block, but the queue is six times slower than needed.
    - **Fix:** One early return after loudness at `analysis.js:271` when both flags are false, filling `tempo` and `keyEstimate` with their existing "disabled" objects; delete the two ternaries at lines 374 and 382.
    - **If we skip it:** Locked-track re-analysis stays six times slower than it needs to be.

15. **A reversed deck that ran out cannot Play again** (`prototype/engine.js:503,528,575-584`; same at `402`)
    - **What this is:** Line 503 wraps a forward deck sitting at the end back to 0 on Play. There is no mirror for reverse, and a finished reverse deck sits at 0.
    - **Problem:** Press Play: the start offset clamps to the last sample, the source ends within one render quantum, `onended` fires, and the Play button flips straight back. Nothing is heard.
    - **Fix:** `if (d.reverse ? d.position <= 0 : d.position >= track.duration) d.position = d.reverse ? track.duration : 0;` at 503 and the same shape at 402.
    - **If we skip it:** Play after a reverse run-out is a dead button until the user seeks.

16. **The documented build command builds nothing; the shipped version is a hard-coded constant** (`desktop/README.md`; `desktop/package.mjs:11,17`; `desktop/package-playback.mjs:14,39`; `desktop/package.json:4`)
    - **What this is:** `npm run package` runs `package.mjs`, which reads version 0.1.6 from `desktop/package.json`. Real builds come from `package-playback.mjs` with `version = '0.1.32'` typed in by hand. `npm start` opens a different entry page and title than the shipped app.
    - **Problem:** Following the README: the output folder for 0.1.6 already exists, the packager logs "Skipping" and returns the old path. No error, no build; the next person tests an 18 October build believing it is current.
    - **Fix:** Delete `package.mjs` and the `package` script; README: bump `version` in `desktop/package-playback.mjs` (or read it from `process.argv[2]`) and run `node desktop/package-playback.mjs`. Load `workspace-preview.html` in `main.cjs` directly so `npm start` matches the package.
    - **If we skip it:** Silent stale builds.

17. **The Python dev server serves the same app with no Content Security Policy and accepts a second origin** (`scripts/serve_prototype.py:22,137-140`)
    - **What this is:** The Electron host sends a strict CSP (scripts only from self plus hashed inline blocks). The dev server sends only `Cache-Control` and `X-Content-Type-Options`. It also accepts `Host: localhost:8768` as well as `127.0.0.1:8768`.
    - **Problem:** Any inline-script sink reached in the browser deployment (finding 9 is one) runs with full access to the library in IndexedDB and the stems API, while the identical page in Electron is blocked. Separately, browsers treat `localhost` and `127.0.0.1` as different origins: import a library on one, open the other from a bookmark, and the library is "gone".
    - **Fix:** In `end_headers`, emit the same CSP string with the hashes computed once from `prototype/index.html` (~6 lines, mirrors `desktop/server.cjs:7-11`). Delete the `localhost` entry from the allowed-host set.
    - **If we skip it:** The browser path has no second line of defence, and a typed URL loses the library.

18. **No automated test touches the engine transport or the persistence logic** (`prototype/*.test.mjs`; `prototype/app.js` top level)

    - **Fix:** (0) Add `startTokens: new Map([[1,1]])` to the fixture at `sync-alignment.test.mjs:13` and a 12-line case: press pending on a deferred `setRate`, `start` in flight, bump the token, release → `start` rejects with AbortError and no align call (executed against the real module by the subagent: passes today). Delete the `> .4` line. (a) `prototype/engine-transport.test.mjs` with a ~80-line fake `AudioContext`; four cases: pause during an awaited start leaves `playing=false` and no voice; `setRate(d,5)` throws and keeps the old rate; `setLoop(d,true,10,10)` throws; Play at the end wraps forward to 0 and reverse to duration. (b) Move `readSavedState(saved)` and `applyAnalysisResult(track, result, snapshot, opts)` out of `app.js` into `prototype/library-state.js` (~45 lines, logic unchanged) with five cases: corrupt JSON → defaults; `crates:{}` → defaults; manual BPM with a revision bump → not overwritten; `replaceTempo` → overwritten; `locked` → untouched.

## Nice to have

19. **Library filtering and analysis re-rendering do more work than needed** (`prototype/app.js:284-320,392-401,1276-1286`)
    - **What this is:** The History crate filter checks every track against every history row (history is never trimmed). Each finished analysis job re-renders the full track table, both decks, the mixer and the overview waveforms.
    - **Problem:** 2,000 tracks × 5,000 history rows is 10 million comparisons per search keystroke. "Analyze all" on 400 tracks rebuilds the decks 400 times while the DJ may be mixing on them.
